FIFA 96 FOR MEGA DRIVE / GENESIS
MEMORY MAP AND REVERSE-ENGINEERING REFERENCE

Revision: 1.1
Date: 2026-10-15
Audience: ROM hackers, 68000 debugger users, and RetroAchievements authors

PURPOSE AND SCOPE
-----------------
This document consolidates the FIFA 96 Mega Drive addresses and values mapped
in the local reverse-engineering work. It separates retail-ROM data, 68000 RAM,
static code locations, and Archipelago-only additions. It is not a claim that
all entries apply to every regional release, ROM revision, emulator core, or
patched image.

The document was prepared by reading existing source, reports, captures, and
logs and by recalculating the vanilla ROM hashes and header checksum. No game,
emulator, client, server, or runtime test was launched to prepare this revision.

IMPORTANT: A memory location belonging to an Archipelago (AP) patch is not a
vanilla-game field. Such entries are explicitly marked AP-ONLY or BUILD-SPECIFIC.

1. EVIDENCE AND CONFIDENCE LABELS
---------------------------------
CONFIRMED-RUNTIME
  The value was read or changed by the running game in an existing BizHawk or
  MAME trace, or was correlated with a real gameplay event. This describes the
  cited build and test conditions; it does not automatically prove every build.

CONFIRMED-STATIC
  The bytes, instruction, pointer table, or address expression was verified in
  ROM or disassembly. Runtime meaning may still be untested.

STRONG
  Several independent observations agree, but an edge case, build, or field
  width is still open.

CANDIDATE
  An address or interpretation worth investigating. Do not build an achievement
  or patch around it without additional verification.

INVALIDATED
  A prior interpretation was disproved or is known to target the wrong field.

AP-ONLY
  Created, reserved, or written by the project patcher/client. It is not an
  original FIFA 96 variable, even when the same MD CART or RAM domain is used.

BUILD-SPECIFIC / HISTORICAL
  Applies to a named AP base or earlier prototype. Do not assume the bytes are
  present in vanilla or in another patch revision.

2. VANILLA ROM IDENTITY
-----------------------
Vanilla image used as the source of truth:

  File name:      fifa96_vanilla.md (raw ROM image; .md is the project extension)
  Size:           2,097,152 bytes (0x200000; 2 MiB)
  Header title:   FIFA Soccer '96
  Product field:  GM T-172086-00
  Region set:     USA/Europe multi-language dump (English, French, German,
                  Spanish, Italian, and Swedish)

Hashes recalculated from the preserved vanilla image:

  MD5:    545b07c1c599f49ea93a4b7b2c7c3782
  SHA-1:  a7fcfe478b368d7d33bcbca65245f5faed9a1e07
  SHA-256: 6a4d606c6f1fa8930e00d317dc8d3edee8f54ac2df2ac835bcb6be6777c35b01

The upload copy is byte-identical to the workspace vanilla image. The SHA-256
above identifies the unpatched 2 MiB image, not an AP ROM or a save file.

The stored Genesis checksum is 0xC9C0 at ROM offsets 0x18E-0x18F. Recalculation
as the sum of big-endian 16-bit words from 0x200 through end-of-file, truncated
to 16 bits, also yields 0xC9C0. Recalculate the checksum after any ROM edit.

3. ADDRESSING AND DATA CONVENTIONS
----------------------------------
3.1 Three address spaces; do not mix them

A. ROM file / BizHawk MD CART offset
   - The ROM image is 0x200000 bytes long.
   - The MD CART domain uses file offsets from 0x000000 through 0x1FFFFF.
   - All ROM offsets in this document are explicitly called ROM offsets or
     MD CART offsets. They are not 68K RAM addresses.

B. MAME 68000 bus address
   - Main work RAM is observed in the 0xFF0000-0xFFFFFF window.
   - Examples: MAME 0xFF03E7, 0xFFE320, and 0xFFF8B5.
   - Task data pointers are often stored as 32-bit sign-extended values such as
     0xFFFF0012; that value is a pointer value, not a ROM file offset.

C. BizHawk 68K RAM domain offset
   - The BizHawk 68K RAM domain is 0x10000 bytes and is base-zero.
   - For the mapped RAM window, the offset is the low 16 bits of the MAME
     address: 0xFF03E7 -> 0x03E7; 0xFFE320 -> 0xE320.
   - In a table, the BizHawk offset and MAME bus address are shown separately.

3.2 Width and byte order

The 68000 is big-endian. A 16-bit word is stored high byte first; a 32-bit
longword is stored most-significant byte first. A byte has no endian order.
Widths below are the width of the mapped field or the read used in the cited
source; an unknown width is stated as unknown rather than guessed.

For example, a score at MAME 0xFFF8B5 is one byte at BizHawk 68K RAM offset
0xF8B5. A SELECT TEAM tab at MAME 0xFF03B0 is a 16-bit word at offset 0x03B0.

3.3 Runtime register bases

- A4 was observed as 0xFF0012 in the SELECT TEAM code path. Thus A4+$39E is
  MAME 0xFF03B0, and A4+$3A0 is 0xFF03B2.
- A5 was observed as 0x00000772 in the relevant disassembly. An A5-relative
  displacement is signed. Derived addresses below are valid only for that A5
  context; A5 is a CPU register, not a fixed global RAM base for every routine.
- ROM disassembly addresses such as 0x7F00 or 0x91BCE are file offsets in the
  local mapping unless the text explicitly labels them as runtime RAM.

behavior of user SRAM.

4.2 Team records

The vanilla team-record table is mapped as follows:

  Base ROM offset:      0x1314DA
  Record count:         240 (IDs 0 through 239)
  Record stride:        0x26 bytes (38 decimal)
  Record name:          record + 0x00, up to 0x10 bytes
  Palette selectors:    record + 0x10, 3 bytes
  Last record start:    0x133854 (ID 239)
  End of table:         0x13387A (exclusive)

The name bytes use the game's character encoding; they are not guaranteed to
be plain ASCII. The three palette bytes are selectors, not RGB colors. The
remaining 0x13 bytes of each record are not fully decoded here.

Examples checked against the vanilla image:

  Team ID 9   Arsenal  ROM record 0x131630  palette 03/0B/0B
  Team ID 80  France   ROM record 0x1320BA  palette 02/0B/03
  Team ID 85  Germany  ROM record 0x132178  palette 07/03/04
  Team ID 234 Zambia   ROM record 0x133796  palette 00/06/03

Address formula: 0x1314DA + (team_id * 0x26). The Champions AP display hook
uses this table for both name and palette selection. The AP-only team-ID byte
is described in section 10; it is not part of the vanilla team record.

4.3 Confederation/team grouping table

ROM offset 0x14A800 is identified in project notes as the start of a two-byte
per-team grouping table, described historically as (conf_id, team_id). Team
IDs in that table were reported unchanged in a patched base while grouping
IDs were reassigned. The exact table extent, field ordering, and group-ID to
visible-tab relationship are not sufficiently consistent across build notes to
use this table as a stand-alone tab lookup. Treat it as CONFIRMED-STATIC for the
observed bytes and CANDIDATE for broad semantic use. Do not assume that a
conf_id is always numerically equal to a SELECT TEAM tab index.

5. 68K RAM MAP
--------------
All addresses in this section are work-RAM addresses. The BizHawk column is the
base-zero 68K RAM domain offset; the MAME column is the corresponding full bus
address. Widths are bytes unless specified. Word and longword values are
big-endian.

5.1 Screen and menu state

BizHawk offset | MAME address | Width | Mapped value / role | Status
---------------|--------------|-------|--------------------|-------
0x03E7         | 0xFF03E7     | 1 B   | Screen ID E7       | CONFIRMED-RUNTIME
0x03E8         | 0xFF03E8     | 1 B   | Additional screen/phase guard; 0x00 in SELECT TEAM | CONFIRMED-RUNTIME
0x03F5         | 0xFF03F5     | 1 B   | Screen phase/substate F5 | CONFIRMED-RUNTIME
0x038C         | 0xFF038C     | 1 B   | Game Settings selected-row index; observed 0, 5, 11 | STRONG

The screen bytes form useful signatures, not a universal state API. See section
6 for the observed pairs and their limitations.

5.2 SELECT TEAM fields

BizHawk offset | MAME address | Width | Mapped value / role | Status
---------------|--------------|-------|--------------------|-------
0x03B0         | 0xFF03B0     | 2 B   | P1 panel tab index; big-endian word | CONFIRMED-RUNTIME
0x03B2         | 0xFF03B2     | 2 B   | P2/opponent panel tab index; big-endian word | CONFIRMED-RUNTIME
0x03B4         | 0xFF03B4     | 2 B   | P1/Home team-record index during SELECT TEAM | STRONG
0x03BC         | 0xFF03BC     | 2 B   | SELECT TEAM focus/side selector | CONFIRMED-RUNTIME

Observed FF03BC values in SELECT TEAM:

  0 = P1 tab row
  1 = P1 team row
  2 = P2 team row
  3 = Player Position Select (the B-button flow)

The focus field is read as a word by the project probes. LEFT/RIGHT changes the
P1 tab only when focus is on value 0. During solo play the second panel belongs
to the CPU. The two tab words are reused by the game during the match and can
contain unrelated values; do not read them mid-match as league IDs. The Client
latches the P2 panel tab while SELECT TEAM is active, rather than treating the
in-match contents of 0x03B2 as a stable opponent field.

Additional A4-relative selection fields found by disassembly:

A4 displacement | MAME address | BizHawk offset | Role / status
----------------|--------------|---------------|--------------
+$0392          | 0xFF03A4     | 0x03A4        | Field touched by selection code; role not resolved
+$0398          | 0xFF03AA     | 0x03AA        | Field touched by selection code; role not resolved
+$039A          | 0xFF03AC     | 0x03AC        | Field touched by selection code; role not resolved
+$03A6          | 0xFF03B8     | 0x03B8        | Field touched by selection code; role not resolved

A4 was 0xFF0012 in the mapped SELECT TEAM path. These addresses are listed as
partially mapped fields, not as confirmed public game variables.

5.3 Game Settings values

BizHawk offset | MAME address | Width | Value mapping | Status
---------------|--------------|-------|---------------|-------
0xE2E4         | 0xFFE2E4     | 1 B   | Language, row 0; English = 0 | CONFIRMED-RUNTIME
0xE2E9         | 0xFFE2E9     | 1 B   | Weather, row 5; 0 Dry, 1 Damp, 2 Drenched, 3 Hot | CONFIRMED-RUNTIME
0xE2EC         | 0xFFE2EC     | 1 B   | Half Length, row 7; 0 = 2 minutes, 1 = 4 minutes | STRONG
0xE2F0         | 0xFFE2F0     | 1 B   | Skill Level, row 11; 0 Semi-Pro, 1 Pro | CONFIRMED-RUNTIME

The settings row cursor at 0x038C was observed at 0 for Language, 5 for Weather,
and 11 for Skill Level. MAME menu descriptors and the option captures identify
Half Length as row 7. The game-settings RAM block around 0xE2E0 is only partially
mapped; do not assign meaning to other bytes from proximity alone.

Weather cycle observed in the menu: 1 -> 2 -> 3 -> 0 -> 1 when moving right.
The AP patch writes the seed Weather into the fresh/invalid-BRAM initializer at
ROM 0x814D2 and sets the initial Weather-unlock mask accordingly. Valid existing
SRAM can bypass the initializer; preservation of a user's saved choice is not
implied by the ROM patch.

5.4 Special-menu setting words

BizHawk offset | MAME address | Width | Meaning / observed values | Status
---------------|--------------|-------|---------------------------|-------
0xE320         | 0xFFE320     | 2 B   | Special settings word 0 | CONFIRMED-RUNTIME
0xE322         | 0xFFE322     | 2 B   | Adjacent Special settings word 1; AP reads/preserves it, bit meanings open | CANDIDATE

Word 0 is big-endian. The AP-mapped rows and value masks are:

  Row 0, Invisible Walls: 0x0001
  Row 1, Curve Ball:      0x0002
  Row 2, Crazy Ball:      0x0004
  Row 8, Balloon Ball:    0x0100

Examples observed in the Special menu include word 0 = 0x0004 for Crazy Ball
alone and 0x0100 for Balloon Ball alone. All four mapped options on is
0x0107. These are value bits in the game RAM word; the corresponding AP unlock
mask is a separate byte in the patched ROM, described in section 8.

Rows 3, 4, 5, 6, 7, and 9 are held Off by the AP patch using mask 0x02F8.
The aggregate labels in source describe these as Dream Team, Super*, and Stupid
Goalie; an individual row-to-label table is not asserted here. Special values
are captured while the Special task is active. The user traces show them
cleared after leaving that task; the exact native writer has not been localized.

5.5 Match scores, clock, and team pointers

BizHawk offset | MAME address | Width | Mapped value / role | Status
---------------|--------------|-------|--------------------|-------
0xF8B5         | 0xFFF8B5     | 1 B   | Team 1 score byte | CONFIRMED-RUNTIME
0xF8B6         | 0xFFF8B6     | 1 B   | Team 2 score byte | CONFIRMED-RUNTIME
0xF8A5         | 0xFFF8A5     | 1 B   | Match clock counter; seconds observed | STRONG
0xF8A7         | 0xFFF8A7     | 1 B   | Related clock byte; diverges from 0xF8A5 | CANDIDATE
0xF89F         | 0xFFF89F     | 1 B   | Nearby counter/phase; meaning unresolved | CANDIDATE

The score bytes were initialized by the game to 0-0 at kickoff; external test

corresponding team byte. The Action Replay labels are "Team 1" and "Team 2".
The project's older HOME/AWAY names are aliases only: they do not guarantee
which team is controlled by a human. Score checks based on positive increments
can observe either team's goals.

The team-pointer candidates above were reported as pointing into the ROM team
name table and persisting during some match captures. Their exact pointer
selection, width, and opponent-ID derivation have not been cross-validated
across all modes/builds. They are not a confirmed substitute for team ID 0x03B4
or the P2 tab captured at SELECT TEAM.

6. SCREEN AND TASK SIGNATURES
-----------------------------
6.1 Screen-byte pairs

MAME E7 | MAME F5 | Screen/context | Notes
--------|---------|----------------|------
0x94    | 0x77    | Title hub / park with Archipelago and Options in AP base | Observed stable signature
0x77    | 0x87    | Post-match Select Mode | Observed stable return-menu signature
0x56    | 0x0D    | SELECT TEAM | E8 must also be 0x00 for the mask hooks
0x22    | 0x1D    | Controllers | Observed signature
0xBC    | 0xE0    | PRE GAME | Observed signature
--      | 0x72    | Title/intro phase | F5 alone was observed; not a complete pair

For SELECT TEAM, the documented AP mask-hook guard is E7=0x56, E8=0x00,
F5=0x0D. A much older prototype used F5=0xF0; that is not the current guard.
Screen-byte pairs can be reused during transitions and must not be treated as a
unique match result without the task/context checks below.

6.2 Task slot layout

The mapped task-0 slot begins at MAME 0xFFFECE, which is BizHawk 68K RAM offset
0xFECE. The project reads 14 bytes:

Offset from slot | Width | Field | Byte order
-----------------|-------|-------|-----------
+0x00            | 4 B   | Update function pointer | Big-endian
+0x04            | 4 B   | Render function pointer | Big-endian
+0x08            | 4 B   | Data pointer | Big-endian
+0x0C            | 1 B   | Task type | N/A
+0x0D            | 1 B   | Task state | N/A

Pointers may be represented as 32-bit sign-extended values, e.g. 0xFFFF0012.
This is a task structure, not an array of independent game flags.

6.3 Native Game Over task signature

The following task-0 tuple was observed at the native result/menu transition:

  Update: 0x00095E72
  Render: 0x000957EE
  Data:   0xFFFF35EA
  Type:   0x09
  State:  0x01

The AP watcher requires two consecutive polls of this tuple in its current
implementation. E7/F5 were not constant across all captures: values such as
0x44/0x41 and 0x00/0x00 occurred in the same flow. Therefore the screen-byte
pair alone is not the Game Over signature. The separate `data` values observed
for Pause and PRE GAME include 0xFFFF500E and 0xFFFF0012 respectively; neither
pointer is a unique match-end flag.

7. SELECT TEAM TABS AND LEAGUE_MASK
-----------------------------------
7.1 Tab-index map

For the AP SELECT TEAM mask path, bit i corresponds to tab index i. The latest
corrected label map is:

Bit / tab | Label
----------|------
0x00 / 0 | American
0x01 / 1 | Brazilian
0x02 / 2 | English
0x03 / 3 | French
0x04 / 4 | German
0x05 / 5 | Italian
0x06 / 6 | Malaysian
0x07 / 7 | Dutch
0x08 / 8 | Scottish
0x09 / 9 | Spanish
0x0A / 10 | Swedish
0x0B / 11 | AFC
0x0C / 12 | Unused/dead tab; blank label in the observed AP data
0x0D / 13 | CAF
0x0E / 14 | CONCACAF
0x0F / 15 | CONMEBOL
0x10 / 16 | OFC
0x11 / 17 | UEFA

Playable bits in the current source: 0-11 and 13-17. Bit 12 is excluded.
The resulting playable mask is 0x0003EFFF. A tested multi-bit example is
0x00030002 = Brazilian + OFC + UEFA.

7.2 ROM mask cores and immediate locations

In the AP base ROM, each core is a six-byte `move.l #mask,D1` instruction:

Instruction ROM offset | Immediate ROM offset | Opcode and value layout | Core
-----------------------|----------------------|-------------------------|-----
0x00007F00            | 0x00007F02           | 22 3C + 4-byte BE mask | A
0x00007F8A            | 0x00007F8C           | 22 3C + 4-byte BE mask | B
0x001FC82A            | 0x001FC82C           | 22 3C + 4-byte BE mask | C
0x001FD570            | 0x001FD572           | 22 3C + 4-byte BE mask | D

The four instruction sites and the four immediate fields are different
addresses. Several early notes call the instruction start the "immediate site";
for an actual longword read/write use instruction_offset + 2. All four cores
must contain the same big-endian mask.

The raw vanilla ROM has 0xFF padding at these locations; the 22 3C cores are
installed by the AP base patch. They are not vanilla code at those offsets.

Core/path notes from disassembly:

  ROM 0x07EC8: gate A code area
  ROM 0x07F4C: gate B code area
  ROM 0x1FC7FC: gate C / backward-floor helper
  ROM 0x1FD538: gate D / backward clamp code
  ROM 0x093260: native tab increment
  ROM 0x093270: right-path clamp hook
  ROM 0x0932E4: second clamp/check path
  ROM 0x092FDA / 0x092FDE: left/backward path and store hook
  ROM 0x093006: secondary test/clamp hook
  ROM 0x093020 / 0x093024: left/backward path and store hook

The hooks clamp the game's selected tab to set bits and wrap across 0..17.
MAME op207/op222 and BizHawk unlock benches confirmed that the group list is
filtered for both P1 and P2 panels. The BizHawk 2.10 / Genesis Plus GX bench
also confirmed that writing the four MD CART immediate longwords at +2 takes
effect while the game is running in SELECT TEAM.

7.3 Default tab immediates

  P1 default tab immediate: ROM 0x092E60, 16-bit BE
  P2 default tab immediate: ROM 0x092E66, 16-bit BE
  Opcode prefix:            ROM 0x092E5E / 0x092E64, bytes 39 7C
  Vanilla observed values:  0x000B at both immediates
  AP seed values:           default tab is set to that seed's starting bit

These are ROM constants, not RAM values. If the starting bit is not zero, the
AP generator changes both defaults so entry does not begin on an unavailable
tab.

7.4 Build values and terminology

- A v38c changelog records a broad-open mask of 0x0003EFFF.
- A later v38e note records 0x0000EFFF as a historical base value. These are
  different AP build snapshots, not two vanilla-game constants.
- The current seed procedure writes a one-bit starting mask to all four cores;
  received league items add bits to that mask.
- In older notes, the four addresses are sometimes called the addresses of the
  immediates. The actual mask data begins two bytes after each 22 3C opcode.
- A team-table conf_id and a visible SELECT TEAM tab index are separate concepts
  until a given build proves their relation.

9. MATCH SCORES, CLOCK, AND END-OF-MATCH LIMITS
-----------------------------------------------
9.1 Confirmed score bytes

  BizHawk 68K RAM 0xF8B5 = MAME 0xFFF8B5 = Team 1 score, 1 byte
  BizHawk 68K RAM 0xF8B6 = MAME 0xFFF8B6 = Team 2 score, 1 byte

Existing BizHawk 2.10 / Genesis Plus GX evidence includes a game-initialized
0-0 kickoff, natural score changes by the game, and retained external test
writes during a match. Real multi-match traces confirmed that the two bytes
track the two team scores. The original Action Replay labels are Team 1 and
Team 2. Do not equate Team 1 with the human player without checking controller
assignment.

9.2 Clock neighborhood

- 0xFFF8A5 / BizHawk 0xF8A5: byte counter tracked displayed seconds in captures
  (for example 51 at 0:51 and 162 at 2:42). Strong match-clock mapping.
- 0xFFF8A7 / BizHawk 0xF8A7: nearby byte follows the clock but diverges in
  captures; it is not an exact duplicate of 0xF8A5.
- 0xFFF89F / BizHawk 0xF89F: nearby small counter/phase field, not fully decoded.

The earlier hypothesis that these three bytes described the opponent was
invalidated by clock-correlated traces. Do not use them as opponent IDs.

9.3 Full-time and victory detection

No standalone stable MATCH_ACTIVE or FULL_TIME RAM byte has been identified.
The task-0 Game Over tuple in section 6.3 is the strongest mapped terminal-menu
signature in the current notes. Screen bytes by themselves are insufficient.

The AP client historically latched the P2 tab at SELECT TEAM and used a later
score result to send a Beat-a-Team check. A user report dated 2026-10-13
identified a false-positive victory check after leaving a match after scoring;
the victory gate is therefore under review. This does not invalidate the score
byte mapping, but it means a score reset or menu transition alone must not be
advertised as a proven win detector.

10.4 Team name and palette redirection

The AP ROM hook redirects the Champions renderer from the fixed Germany record
(ID 85, ROM 0x132178) to the latched Home team ID. Name and palette are redirected
together using separate hooks at 0x088D8C and 0x088D20. If no played Home team
has been latched, the source defines France (ID 80) as the fallback. In the
AP ROM, the dynamic team ID is stored at MD CART 0x1FE10A; in vanilla, the
normal records remain at 0x1314DA + ID*0x26.

A diagnostic MAME display substitution at code sites 0x0AD0CE and 0x0AD30E
was used in a cold-call investigation to redirect the displayed name only.
That diagnostic was not a change to the internal team ID and is not the AP
production hook. A displayed name without matching palette is not proof of a
coherent team identity.

12. CANDIDATES, INVALIDATED LEADS, AND BUILD DIVERGENCES
--------------------------------------------------------
12.1 Invalidated or unsafe interpretations

1. RAM 0xFF0A00 (BizHawk 68K RAM offset 0x0A00) is NOT a free league-mask
   variable. A RAM-mask prototype observed game data 0x02F802F1 there at park;
   the game overwrote the injected mask and produced invalid tab behavior.
   The supported project path is the four MD CART immediate longwords.

2. The old opponent hypothesis for 0xFFF89F / 0xFFF8A5 / 0xFFF8A7 is invalid.
   0xF8A5 follows displayed seconds; 0xF8A7 is related but diverges; 0xF89F
   remains unresolved.

3. The old tab map that assigned CAF to bit 12, CONCACAF to bit 13, and
   CONMEBOL to bit 14 is superseded. The corrected map is bit 12 unused,
   bit 13 CAF, bit 14 CONCACAF, and bit 15 CONMEBOL. The early op221 visual
   report itself says CONMEBOL had not yet been observed; use the later
   corrected source/evidence, not that early table in isolation.

4. ROM mask-core addresses 0x7F00, 0x7F8A, 0x1FC82A, and 0x1FD570 are not
   vanilla code in the preserved retail ROM; those offsets contain 0xFF fill.
   They become `move.l #mask,D1` only after the AP base patch.

5. E7/F5 screen bytes alone are not a universal Game Over or win flag. The
   task tuple and match context are required for a reliable terminal state.

6. 0x03B0 and 0x03B2 are SELECT TEAM tab fields, not stable in-match league
   fields; the game reuses them during play.

7. 0xFFE331 is a legacy feature-bit field, not the Friendly/Archipelago
   SELECT TEAM league mask. The mask is in the four ROM code immediates.
   Likewise, the legacy $DA66(A5) / ROM 0x09AE path is not the tab clamp.

8. The 0xBE6 teardown helper is not the Special action. The relevant
   Options -> Special task route is the separate nexttask selector-2 path.

12.2 Open candidates and limits

- The exact opponent team ID during play is not settled. 0xE51C, 0xE520, and
  0xE788 are pointer candidates; 0x03B2 is a reliable P2-panel tab only while
  SELECT TEAM is active.
- The exact role of RAM fields 0x03A4, 0x03AA, 0x03AC, and 0x03B8 is open.
- The full structure/extent and label crosswalk of ROM 0x14A800 is not
  consistently documented across the historical conf-table builds.
- No stable full-time or match-active RAM byte is mapped.
- The exact native writer that clears 0xFFE320/0xFFE322 after leaving Special
  has not been located.
- The AP Champions post-match Select Mode to task-0x22 handoff was confirmed
  in a user-run E2E test on 2026-10-13. The exact APWorld/seed version and the
  effective native PC/D0 argument were not established by that run; keep those
  CPU-level details open rather than describing the E2E handoff as unvalidated.
- A5-relative fields outside the direct score/settings map have incomplete
  width/value semantics. Recalculate them only in the corresponding A5 context.
- Valid SRAM can bypass the fresh/invalid-BRAM Weather and Half Length default
  initializer. Do not infer how a user's saved setting will survive from the
  ROM immediate alone.

12.3 Conflicting evidence and precedence

- Early memory-domain notes sometimes mixed full MAME bus addresses with
  base-zero BizHawk RAM offsets. The convention used throughout this document
  is BizHawk offset = MAME address & 0xFFFF for the mapped 0xFFxxxx RAM window.
- Early tab-label notes assigned CAF, CONCACAF, and CONMEBOL to earlier bit
  numbers. The corrected map in section 7 is the one to use; the first visual
  probe did not by itself establish the final CONMEBOL mapping.
- The v38c AP-base snapshot had a reported checksum of 0x9E67. That checksum is
  not the vanilla checksum and is not universal across later seed images.
- A ROM offset can contain different bytes in retail vanilla, an AP base, and a
  per-seed image. Identify and hash the exact target image before patching.
- Where evidence conflicts, the status labels in this document preserve the
  uncertainty instead of promoting an early hypothesis to a confirmed fact.

13. STANDALONE USE AND PATCH SAFETY
-----------------------------------
This reference is intended to be read on its own. It distinguishes the vanilla
image, AP-only additions, runtime RAM, and ROM code offsets, and records open
questions where the available evidence is incomplete.

Before using any address in a patch:

1. Identify and hash the exact ROM image and confirm its region/revision.
2. Confirm that the target bytes match the expected original bytes; abort if
   they do not.
3. Confirm whether the address is a ROM file offset, a full 68K bus address,
   or a BizHawk 68K RAM-domain offset.
4. Preserve instruction boundaries, data width, big-endian order, task context,
   and code-cave bounds.
5. Recalculate the Genesis checksum after a ROM edit.
6. Verify the write by readback and verify its in-game effect separately. A
   successful memory write alone does not prove the intended game behavior.
