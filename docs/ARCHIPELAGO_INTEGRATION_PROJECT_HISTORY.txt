FIFA 96 MEGA DRIVE ARCHIPELAGO INTEGRATION
PROJECT HISTORY AND RECONSTRUCTION

Status cutoff: 2026-10-15
Language: English

===============================================================================
1. PURPOSE, DATE RANGE, AND EVIDENCE RULES
===============================================================================

This is a self-contained history of the work that turned FIFA 96 for Mega Drive
into a working Archipelago world, ROM patch, and BizHawk client. It is written
for ROM hackers who may want to understand both the implementation and the
failure modes. It includes the starting design, the changes in scope, dated
milestones, user-run acceptance results, and the parts that remained uncertain.

The earliest detailed chronology that can be reconstructed starts on
2026-09-30. Tasks 1 through 3 predate that point, but the intermediate ROMs,
build scripts, and some working notes were lost during an accidental cleanup
on 2026-09-30. A surviving session note identifies Task 3 as delivered in
version v35mC, and later ROM binaries retain several features from those tasks.
That is not enough to recreate their exact dates, implementation steps, or
individual test results. This history does not fill those gaps by guessing.

The project record combines different kinds of evidence. They must not be
confused:

- Static disassembly and source inspection establish code paths, offsets, and
  hypotheses, but do not alone prove a live game behavior.
- Offline tests and emulator harnesses can establish targeted behavior, but a
  simulated goal or forced state is not the same as a natural match event.
- User-run end-to-end tests are the source of the final gameplay acceptance
  evidence. A location is counted only when the client sent the check and the
  AP FileLog or equivalent receipt confirmed it.
- A RAM/configuration value proves what the game or client read at that moment;
  it does not by itself prove that a Special option visibly affected gameplay.
- Universal Tracker completion is a separate result from AP location checks.
- A successful route on one menu is not proof of a different route that happens
  to lead to the same screen.

The assistant did not launch a game, emulator, AP client, AP server, or runtime
test during the final history/documentation pass. The 2026-10-14 beta sessions
and the decisive 2026-10-13 Champions tests were run by the user. Earlier dated
development records also include static tests, offline harnesses, and MAME or
BizHawk development runs; those are described only at the level their records
support.

===============================================================================
2. WHAT THE INTEGRATION BECAME
===============================================================================

The final randomizer did more than swap a few bytes in a ROM. It connected four
layers:

1. The Archipelago world creates a seed with a starting league, unlock items,
   goal medals, settings, and checks.
2. The generated procedure patch applies seed-specific values to a supported
   vanilla image.
3. The BizHawk client reads game state, sends location checks, receives items,
   updates the league mask and settings, and confirms memory read-backs.
4. The AP-patched ROM supplies the team-selection gates and a guarded native
   Champions-screen handoff, while leaving FIFA 96's task lifecycle intact.

The final beta checklist contained 127 AP locations:

- 100 cumulative Home goals;
- 17 wins against the different team-tab groups;
- 4 Weather win checks;
- 2 difficulty win checks;
- 4 Special-setting win checks.

The completion condition was separate from those 127 locations. In the final
beta run, the configured 100/100 Medal goal, Archipelago Victory/completion,
and Champions display were recorded separately from the 127/127 location
count.

The project began with a simpler Manual-like design: 17 league unlocks, 50
Medals, 17 Beat Team checks, 50 goal checks, and a 40-Medal goal. It evolved into
configurable goal-count and Medal-percentage options, actual match-setting
checks, robust native win detection, and a Champions screen that could be
reached after a match or when the player was already at the title menu. Later
scope decisions removed an experimental RAM-mask option and an unimplemented
DeathLink placeholder rather than expose unfinished features.

3. CHRONOLOGICAL HISTORY
===============================================================================

BEFORE 2026-09-30: THE INHERITED ROM WORK
----------------------------------------

The surviving ROM contains the title-screen word "Archipelago", renamed or
replaced title slots, confederation/team groups, AP player routines, and league
selection gates. The notes identify Task 3 as version v35mC, but its exact
changes are not reconstructible. The early Archipelago skeleton was modeled on
Manual-style FIFA worlds: league unlocks as progression items, Medals as goal
currency, Beat Team and goal checks, and a selected starting league.

The exact first user request is not fully recoverable. The dependable starting
point is the surviving design and ROM: make the Mega Drive game's locked league
tabs usable as Archipelago progression, then connect in-game events to items
and locations. Weather, difficulty, Special effects, an adjustable goal count,
and the end-screen presentation were later additions or expansions.

2026-09-30: SPECIAL MENU ROUTING, ROM UI, AND FIRST AP WORLD SKELETON
--------------------------------------------------------------------

A substantial portion of the day was spent restoring the working record after
the accidental deletion of intermediate ROMs and development files. That wipe
is why the first tasks cannot now be reported with the same confidence as the
later beta.

The immediate ROM task was to make OPTIONS -> Special open FIFA 96's native
CHEATS menu. The first attempted approaches put a trampoline at a shared video
teardown site and tried to create the Cheats task while the OPTIONS task was
still alive. They produced an allocation error. Disassembly showed that the
shared site was not the Special action dispatcher. The native FETASK_nexttask
path ends the parent task before spawning its successor. Changing the task ID
at the proven dispatcher entry, from 0x1A to 0x1D, solved the problem with a
one-byte ROM change. This became the key method lesson: trace the actual task
arguments and lifecycle before patching a nearby jump or shared teardown.

The next UI revisions fixed several problems discovered during the same menu
work: Special had been gray or visually inconsistent, Removed entries had the
wrong color, and Start from CHEATS returned to the wrong screen. The corrected
path returned to OPTIONS, with Special displayed as an enabled menu item.
MAME screenshots and task traces supplied targeted evidence for these UI
changes.

The AP world skeleton was assembled around the four ROM instructions that
clamp the SELECT TEAM tabs. A test initially suggested that some multi-bit
league masks were locked or invalid. Disassembly showed the clamp scans forward
or backward for the next set bit and wraps; it can support multiple set bits.
The apparent lock was a navigation mistake: the test moved focus to Player 2's
panel instead of cycling Player 1's tab row. The practical correction was to
focus the Player 1 tab row first and use Player 1 navigation.

The initial design used a 32-bit league mask, one bit per tab, and the standard
Archipelago model of starting inventory, progression items, checks, and filler.
The project began from an AP world skeleton, not a finished gameplay client.

2026-10-01: LEAGUE ITEM LOOP, SCORE RAM, AND BEAT TEAM CHECKS
------------------------------------------------------------

The first client work concentrated on applying league unlocks safely. The four
mask instructions are 68K `move.l #mask,D1` sites. The mask data is the
longword at instruction start plus two bytes, not the opcode. An early client
write targeted the opcode; correcting the write to the immediate field fixed
it. The four instruction starts are 0x7F00, 0x7F8A, 0x1FC82A, and 0x1FD570.

BizHawk memory-domain handling also had to be made explicit. The cartridge
program image is exposed as MD CART in the tested setup; RAM is exposed through
a different domain and address convention. The client resolves the domain,
translates the address, writes all four mask immediates, and reads them back.
That read-back is important: an attempted write is not proof that the emulator
or game accepted it.

A RAM-based league-mask alternative was explored. A test address at 0xFF0A00
was later measured as occupied by ordinary game data, so that approach could
corrupt active state. It was retained only as an experimental branch at first,
then removed from the user-facing options on 2026-10-14. The tested release
path remained the four ROM immediates.

An early default-mask mistake treated the four bytes or opcodes as if they were
the mask itself. The client was changed to validate that the ROM actually
contains the AP mask instructions before reading or writing a seed mask. The
seed's starting league is precollected, removed from the random item pool, and
used to initialize the mask. Pool-size and uniqueness checks were added so the
starting league cannot also appear as a duplicate unlock.

Score detection progressed from uncertain RAM guesses to confirmed game
addresses. Home score is at 68K RAM offset 0xF8B5, Away score at 0xF8B6, and the
match clock at 0xF8A5. The earlier candidate triplet that included 0xF8A5 was
not an opponent-team structure; 0xF8A5 is the clock. The distinction was
established by observing score initialization, natural CPU score increments,
and clock correlation.

The client then connected Home goals to immediate cumulative checks. The full
item/check loop was exercised in a development harness: a goal check was sent,
the server returned an item, the client updated the mask, and the cartridge
read-back matched. That harness used a simulated goal, so it was not treated as
proof of a complete natural match.

Beat Team checks required a different memory strategy. The opponent's league
tab is stored at 0x03B2 during SELECT TEAM, but the same words are reused later
in gameplay. The client therefore captures the tab during the correct menu
context and remembers it for the match. An initial win check was tied to a
later 0-0 score reset; the project kept Beat Team separate from immediate goal
checks and refined the exact win gate in subsequent sessions.

2026-10-02: NATURAL GOALS, PERSISTENT PROGRESS, AND AN UNRESOLVED FREEZE
-----------------------------------------------------------------------

Goal checks were changed to fire immediately for each new Home goal rather
than waiting for the next match. A match-active latch was added so stale score
bytes outside an active match could not create phantom goals. Beat Team remained
a separate victory result. The goal count needed to persist across match
transitions and client restarts, not just within one Python process.

A user-run test supplied natural goal evidence: two Home goals produced two
separate goal checks and AP item receipts. The user later reported that the
game stopped in the second half on the game's "SEGA Library Internal Error"
for match ID 3204. The user closed BizHawk after the freeze; that closure was
not evidence that the emulator had closed itself. The supplied image and logs
did not establish a cause. The checked ROM had the expected baked-in mask and
checksum, and the two goal items had already arrived before the freeze. No
causal link to the AP client, mask write, ROM patch, or emulator was proved.
Later beta games completed normally, but that does not retrospectively identify
or prove a fix for this specific early freeze.

A separate client-restart issue was also found: if the client restarted, its
local cumulative counter could return to zero while the server still remembered
previously checked goal locations. A later client restored cumulative goal
progress from AP's checked locations; on 2026-10-14 beta runs, the log showed
that restoration explicitly.

2026-10-04: GAME SETTINGS MEMORY MAPPING
---------------------------------------

The project expanded beyond league locks and goals. The Game Settings menu was
mapped for settings that could be randomized or checked. Memory observations
identified the in-game Weather and difficulty values, menu rows, and related
fields; other settings such as language and half length were also investigated.
The important design change was to make setting checks depend on the value
actually present for the match, not simply on an item that had been received or
a menu choice remembered earlier.

At this point, menu navigation and memory layout were still being worked out.
A screenshot or a RAM value was useful for locating a setting, but was not yet
proof that the corresponding match check fired or that the visible effect was
active during gameplay.

2026-10-05: SPECIAL SETTINGS, SECRET-MENU INPUTS, AND CONTROL GUARDS
--------------------------------------------------------------------

The Special menu's memory representation was measured without writing RAM.
The two Special words are at 0xFFE320 and 0xFFE322. The four binary settings
that later became AP checks have these first-word bits:

- Invisible Walls: 0x0001;
- Curve Ball: 0x0002;
- Crazy Ball: 0x0004;
- Balloon Ball: 0x0100.

Other Special entries can encode team-specific states in either word. The
client therefore needed to filter, preserve, and verify the exact supported
bits rather than copy a menu word blindly.

A separate control-path issue concerned the game's Secret Menu shortcut. The
OPTIONS -> Special entry and the pre-match B shortcut converge on native
Cheats, but they are not the same menu action. A guard was developed so the
non-OPTIONS B entry points did not create the Secret Menu task, while preserving
the OPTIONS -> Special route. The PRE GAME route was directly verified; the
other shortcut branches, including stable Pause and Half-Time contexts, were
not all reproduced visually. The record deliberately does not describe those
unreproduced branches as individually validated.

2026-10-06: SPECIAL-MENU NAVIGATION AND B-GUARD FOLLOW-UP
--------------------------------------------------------

Follow-up tests concentrated on reliable controller focus and the boundary
between the OPTIONS entry and non-OPTIONS shortcut paths. A key general lesson
was to label each tested input and screen context. A tested PRE GAME shortcut
is evidence for that path, not for Pause or Half-Time. The menu and ROM guards
were kept narrow enough to preserve the known OPTIONS -> Special -> CHEATS
behavior.

2026-10-07: UI AND SPECIAL-STATE VERIFICATION CONTINUED
-------------------------------------------------------

The Special menu work continued with visual and memory-state checks. This
reduced uncertainty about which row was being changed and which word/bit
represented the selected value. It still did not establish the later AP
requirement that a setting remain On at kickoff and produce an eligible
post-match check; that required a separate client persistence change and user
beta evidence on 2026-10-14.

2026-10-08: CONFIGURABLE GOAL COUNTS AND COMPLETION SEMANTICS
------------------------------------------------------------

The original fixed set of 50 goal checks was generalized. The world gained a
configurable goal-check count from 10 through 100 and a configurable goal-Medal
percentage from 10 through 100 percent, with an 80 percent default. The integer
completion threshold is the ceiling of goal count times percentage, bounded
between one and the configured maximum.

The Victory condition was made a completion state rather than a location that
could be filled but was not reported by the client. Existing location IDs were
kept stable where possible; higher goal thresholds were added without
renumbering the existing ones. The world rules and client were updated together
so the number of generated goal locations, the Medal pool, and the completion
threshold agreed.

2026-10-09: NO RELIABLE NEW DAILY MILESTONE PRESERVED
----------------------------------------------------

The surviving dated record does not establish a distinct integration milestone
for this date. This is a gap in the chronology, not a claim that no work took
place.

2026-10-10: CHAMPIONS-SCREEN ROUTING AND TEAM IDENTITY RESEARCH
--------------------------------------------------------------

The user-facing goal expanded from completing an AP objective to presenting
the game's native Champions screen at the right time. The desired result was
not just a forced task ID: it had to preserve the game's task lifecycle and
display the correct Home team's name and palette. The route also needed to work
when the goal was reached without a match and the player was already at the
title/Select Mode hub.

Static disassembly identified a native task-creation route that could create
task type 0x22. A MAME run showed the task being created, but early captures did
not establish every aspect of the complete Champions scene or the AP
post-match route. A direct task-state force had caused an allocation error in
a diagnostic attempt, reinforcing the need to call the native task machinery at
a safe, observed entry point.

In parallel, the Secret Menu B guard was assembled around six non-OPTIONS
entry points. The PRE GAME path was directly tested; the implementation was
broader than a run-time test of exactly three named screens, so Pause and
Half-Time behavior remained a stated coverage limit.

2026-10-11: HOME TEAM LATCHING AND CHAMPIONS IDENTITY
----------------------------------------------------

The Champions renderer used a fixed team record in the base game. The AP
extension added a runtime Home team ID and separate display hooks for the team
name and palette. This prevented a display-only substitution that could show
a name and colors belonging to different teams.

An important correction was to latch the Home team only after a recognized
kickoff. A selected Home team, a controller screen, or a pre-game settings
screen does not prove that the player actually started a match. The client
therefore waits for a known kickoff signature before treating a Home team as
played. The no-match fallback behavior was added and validated later, during
the 2026-10-13 title-hub test.

2026-10-12: MATCH START, WEATHER DEFAULTS, AND DEFERRED CHAMPIONS HANDOFF
------------------------------------------------------------------------

Match-start detection was tightened. PRE GAME signatures, known kickoff
signatures, and an observed clock transition were combined so an unknown screen
or stale nonzero clock could not start a match in the client's state machine.

A seed configured with Dry weather exposed a real default-path mismatch. The
slot data and starting item said Dry, but a kickoff snapshot said Damp. Static
inspection found that the fresh/invalid-BRAM initializer still hard-coded Damp.
The ROM patch now substitutes the seed's starting Weather on that path, and the
client normalizes a locked setting at PRE GAME with a RAM write and read-back.
A valid saved BRAM/SRAM can bypass the fresh/invalid-BRAM initializer, so the
ROM immediate alone is not proof of what a particular saved game will start
with.

Champions completion could occur during a match, but the visual scene should
not interrupt the match. The client therefore latches completion immediately
and waits for a stable title/Select Mode screen before requesting the native
scene. The cold title hub and post-match Select Mode use different task-0 data
pointers: 0xFFFF1A36 for the cold title-hub context and 0xFFFF0012 for the
post-match context. They require separate guards and separate validation.

User testing of the post-match route involved many failed or partial attempts.
Full-time detection, clock transitions, controller timing, and the distinction
between the result menu and quit confirmation all needed careful separation.
The user clarified the real quit prompt sequence as P1 C, then P1 Up to select
Yes, then P1 C. Earlier assumptions about a different direction were corrected.

2026-10-13: POST-MATCH CHAMPIONS SUCCESS, TITLE-HUB FALLBACK, AND WIN-GATE
-------------------------------------------------------------------------

During the post-match investigation, the user clarified that the visible title
hub and Select Mode are the same menu context for this feature, while Select
Team is a different screen. This distinction matters: the early failed handoffs
really did land on Select Team, not the requested Champions screen.

The post-match Champions route had several genuine failures before it passed.
Candidate builds 0.5.6 and 0.5.7 armed the AP request but returned to Select
Team; no task-0x22 callback was confirmed in those runs. A newer trace showed
the post-match task in state 0x40 and phases including E7/F5=0x77/0xBC, but
did not capture a reliable effective PC/D0 value at the native dispatcher.
The phase sequence was a useful observation, not proof that one phase alone
caused the failure.

Later on 2026-10-13, a user-run post-match E2E test succeeded. The AP goal was
reached during a match; the client waited for the return to Select Mode, armed
the request without writing the selector RAM, and observed the native task
0x22 appear. The client acknowledged the task and cleared the request. A user
capture showed the Champions screen with Zambia, Home ID 234, and palette
00/06/03. The exact APWorld or seed version was not printed in the logs. This
is a valid end-to-end success for the post-match path, while the exact native
PC/D0 argument and low-level dispatcher path remain unproven.

A separate user-run no-match test later reached the completion threshold while
already at the title hub. With no played Home team, the client chose France
(ID 80, palette 02/0B/03), created task 0x22, cleared the request, and the user
confirmed Champions. This independently validated the cold title-hub fallback;
it does not substitute for the distinct post-match result above.

The same day exposed a false win-check problem. A match could produce a goal,
then be abandoned, and the transition back to the title could be mistaken for
a win. The user required non-goal win checks to be evaluated only at the native
GAME OVER screen; goal checks were to remain immediate. Screenshots from a
penalty shootout showed the game's final GAME OVER display as 1-0 after a 5-2
shootout, but that run had no AP log and proved no AP location receipt. It
clarified the visible result, not the full AP behavior for penalties.

2026-10-14: HOST COMPATIBILITY, GAME OVER FIXES, AND TEN BETA PARTS
-------------------------------------------------------------------

This was the main user acceptance day. Before and during the beta, the project
also corrected several packaging and behavior issues.

Archipelago's room page did not display the download link for newly generated
patches because the slot's canonical game name was "Fifa Soccer 96 Megadrive"
while the patch manifest declared the legacy name "Fifa96". The package was
updated to generate new manifests with the canonical game name and to retain a
legacy compatibility handler for old patches whose manifest says `game:
"Fifa96"`. The `.apfifa96` extension stayed the same. Existing seeds and
patches were not rewritten. The release artifact uses the single canonical
filename `fifa96.apworld`; the file itself is replaced rather than given a
numbered version name.

Two placeholder or experimental options were removed at the user's request.
The user-facing RAM-mask option was removed because the tested and supported
path was the four ROM immediates. DeathLink was also removed because it had no
implemented behavior. Historical seeds and user-provided archives were left
unchanged.

The native GAME OVER gate was corrected to use the stable terminal task tuple
rather than a volatile screen-byte pair. A user-run test confirmed the important
negative case: after scoring and abandoning a match, the goal check still fired,
but Weather, Skill, and Beat Team win checks did not. In a later real 2-0
victory, those non-goal checks fired at GAME OVER and their AP rewards were
received. The item notification text was also confirmed by the user to display
in BizHawk.

A separate Beat Team bug was found when the opponent-tab word reset during the
transition out of SELECT TEAM. The client had captured a transient zero and
could lose the true UEFA tab before GAME OVER. Capture was restricted to
SELECT TEAM while the active selection task was present, so a transition task
could not overwrite the saved opponent group.

Special-setting persistence took several iterations. In the early beta, the
menu contained On values but both words were zero at kickoff, so those matches
were not eligible for the Special win checks. A client mitigation captured the
selected supported bits, reapplied them during match preparation, and verified
them by RAM read-back. A further multi-bit latch preserved newly selected
Specials through the next confirmed kickoff even when a later sample appeared
Off. The exact native routine that originally cleared the values was not
identified.

===============================================================================
4. CONSOLIDATED TECHNICAL DESIGN
===============================================================================

VANILLA BASE AND PATCH PIPELINE
-------------------------------

The supported baseline is a 2 MiB FIFA 96 Mega Drive image. The recorded
vanilla SHA-256 is:

  6a4d606c6f1fa8930e00d317dc8d3edee8f54ac2df2ac835bcb6be6777c35b01

The seed creates a procedure patch from this supported base and records seed
values in the patch data. A ROM offset must always be interpreted against the
exact image being patched: vanilla padding, AP base code, and a seeded image
can contain different bytes at the same offset. The patch builder checks
expected source bytes and recalculates the Genesis checksum.

The public Archipelago game name is `Fifa Soccer 96 Megadrive`. New patch
manifests use that same canonical game identity. Compatibility remains for
older `.apfifa96` patches whose manifest says `game: "Fifa96"`; a renamed public
identity must not strand already-generated legacy patches.

LEAGUE MASK AND ITEM DELIVERY
-----------------------------

The AP league mask is a 32-bit value installed into four ROM immediates at
instruction start + 2:

  0x7F00, 0x7F8A, 0x1FC82A, 0x1FD570

The client updates all four sites when unlock items arrive and reads them back.
The tested release uses the ROM-immediate route, not the abandoned experimental
RAM-mask option. In the BizHawk setup used for the project, MD CART is the
cartridge image domain and 68K RAM is a separate runtime domain. Full MAME
addresses in the 0xFFxxxx region must not be passed unchanged to a base-zero
BizHawk RAM API.

The starting league is precollected and removed from the random pool. A mask
bit represents a team tab, not an arbitrary team name. Confederation bit labels
were corrected during reverse engineering; a wrong label-to-bit table can make
a valid bit look like a broken lock.

GOALS, MATCH STATE, AND BEAT TEAM
---------------------------------

Home score is read at 0xF8B5 and Away score at 0xF8B6. The clock at 0xF8A5 is
not an opponent ID. Goal checks are cumulative and immediate: a new Home goal
sends the corresponding threshold check without waiting for the match to end.
The client restores cumulative progress from checked AP goal locations after a
reconnect, and it gates score interpretation on a confirmed active match so
stale menu bytes do not count as goals.

Beat Team is a separate event. The opponent tab is captured at SELECT TEAM
from 0x03B2 and retained through the match. It is not safe to keep sampling
that word during gameplay or task transitions because FIFA 96 reuses it and
can reset it before the final result is processed.

Win checks for Weather, difficulty, Special, and Beat Team are evaluated only
at the native GAME OVER result, not merely because the score resets, a user
quits, or the game returns to the title. Goal checks remain immediate. The
terminal task tuple is stronger evidence than a volatile E7/F5 screen-byte
pair; the GAME PAUSED task uses a different data pointer.

SETTINGS AND EVIDENCE
---------------------

For Weather and difficulty, the client checks the match's actual setting, not
only the item inventory. For the four supported Special checks, it captures
the selected bits, reapplies them before kickoff when needed, reads back RAM,
and bases eligibility on the kickoff snapshot. The first successful Special
runs distinguish the menu value, the applied value, the match snapshot, the
resulting client check, and the AP receipt.

That sequence is a general ROM-hacking test pattern:

  user selection
    -> memory value in the menu
    -> client application and RAM read-back
    -> value at confirmed kickoff
    -> actual match result
    -> client check sent
    -> AP receipt

Each arrow needs its own evidence. A displayed menu setting is not proof of
a match setting. A memory bit is not proof of a visual gameplay effect. A
locally logged check is not proof of server acceptance until the receipt is
seen.

CHAMPIONS HANDOFF
-----------------

The AP extension stores request, completion, Home team ID, and hook markers in
reserved ROM bytes. It waits for the correct native menu/task context and uses
native task creation rather than writing a task ID into a live task structure.
The Champions task is type 0x22, with observed update function 0x000A04B4 and
render function 0x0009FE8E.

The cold title-hub context uses task-0 data pointer 0xFFFF1A36. The distinct
post-match Select Mode context uses 0xFFFF0012. Completion reached in a match
can be latched immediately, but the visible handoff waits for a stable menu.
If no played Home team has been latched, France is used as the fallback.
Separate E2E successes exist for the no-match title hub and post-match Select
Mode. The post-match test did not record the effective native PC/D0 value, so
that low-level call detail remains open even though the visible route passed.

===============================================================================
5. SCOPE CHANGES AND WHAT REMAINS OPEN
===============================================================================

HOW THE REQUEST EVOLVED
-----------------------

The project grew in distinct stages:

- First, expose the hidden AP/league selections and use ROM gates for league
  unlocks.
- Then, turn goals into immediate locations and make goal progress survive
  match changes and client reconnects.
- Add opponent-tab wins, Weather, difficulty, and Special checks based on the
  settings actually in force for a match.
- Replace a fixed goal count with configurable goal checks and a configurable
  Medal completion percentage.
- Add native Champions presentation, including a correct Home team identity,
  a no-match fallback, and a separate post-match route.
- Remove features that were experimental or placeholders: the RAM-mask toggle
  and DeathLink were not left exposed as if they were finished.
- Preserve old `.apfifa96` compatibility while using a canonical game name for
  new patch manifests and the stable, unnumbered `fifa96.apworld` release name.

OPEN OR LIMITED AT THE CUTOFF
-----------------------------

1. Early Tasks 1-3 cannot be reconstructed in full because intermediate build
   artifacts and notes were lost. Only surviving ROM features and the v35mC
   delivery label are dependable.

2. The post-match Champions route passed end to end on 2026-10-13, but the
   effective native PC/D0 argument at the dispatcher was not captured. The
   exact APWorld/seed version used by that run also was not printed. Do not
   downgrade the E2E success to "unvalidated"; do not overstate the low-level
   reverse engineering either.

3. A true GAME OVER after a normal win and the negative case of quitting after
   a goal were confirmed. A 5-2 shootout was visually shown to produce a final
   displayed 1-0 GAME OVER score, but that older run did not include AP logs.
   A later penalty/UEFA run exposed an opponent-tab capture bug; the capture
   guard was corrected, but a post-correction AP penalty run was not recorded.
   Full post-shootout check coverage therefore remained open.

4. An early second-half internal error, match ID 3204, was not attributed. Later
   completed beta matches did not provide a root cause for that distinct event.

5. Special setting bits and AP checks were validated through kickoff and AP
   receipt. The visual effectiveness of every Special in every combination was
   not established by those memory logs. The user specifically observed only
   Balloon Ball as visibly active in one run where Curve, Crazy, and Balloon
   were all present in the kickoff memory snapshot; the two kinds of evidence
   must stay separate.

6. Universal Tracker at 100 percent was reported by the user, but no matching
   UT log was supplied in the cited beta evidence. It remains a separate
   user-reported validation, not part of the 127 AP location count.

7. The user reported that the Lua debugger slowed the game after matches and
   could coincide with missed inputs. The user considered it low priority. No
   cause was established and no change is represented as a confirmed fix.

8. The early shortcut guard directly demonstrated PRE GAME behavior and the
   OPTIONS path; Pause and Half-Time were not each independently reproduced
   and visually verified in the final focused tests.
